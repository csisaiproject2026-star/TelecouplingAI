# MSU 200-User Capacity Validation Report

**Date:** 2026-07-28

**Target:** `https://ai.telecoupling.msu.edu/` through the MSU public WAF

**Candidate:** `capacity-200-v1-ea641be`

## Executive conclusion

**PASS for the tested scope:** 200 independent users each uploaded a small CSV
input and ran one fast tool through the public MSU WAF. All 200 runs completed,
all 200 sessions were retained, and no API, Redis, Celery, nginx, container, or
host failure occurred.

This result does **not** prove unrestricted 200-user capacity for simultaneous
large uploads, 200 heavy InVEST jobs, or repeated multi-step workflows. Those
remain separate capacity gates.

## Candidate deployed for the test

The original MSU API still had `MAX_SESSIONS=50` and did not expose the capacity
health endpoints. A thin candidate image was built from the existing MSU
backend image with the exact runtime capacity source from Git commit `ea641be`.

Effective settings:

Twenty-nine focused API, session, Gemini-capacity, timeout, and fast-worker race
tests passed before the API was switched. Only `api-server` was recreated;
Redis, Celery workers, nginx, data, keys, and server-specific URLs were not
restarted or replaced.

## Test method

- Public route: MSU WAF -> origin nginx -> API -> Gemini -> Redis/Celery.
- Arrival window: 30 seconds for the 50/100/200-user stages.
- One persistent session and one fast tool run per user.
- Tools: OLS, CO2 Emissions, Cost-Benefit, and Food Security.
- Each tool used a small inline CSV upload.
- Acceptance gate: at least 99% completed runs and 100% test-session retention.
- Absolute client deadline: 900 seconds.
- Server metrics sampled throughout the ladder.
- TPM reservations were allowed to clear between stages.

## Initial diagnostic runs

Two non-acceptance runs were retained as diagnostic evidence:

1. The first 10-user attempt produced 3/10 because the local test process
   inherited a `127.0.0.1` HTTP proxy that admitted only three concurrent
   connections. Only those three requests reached the WAF/origin. The direct
   WAF rerun passed 10/10.
2. The original Cost-Benefit test prompt included the word `analysis` in the
   function name. This repeatedly triggered the application's workflow-plan
   path: all 2 Cost-Benefit cases in the 10-user stage, all 8 in the 50-user
   stage, and all 34 in the first 100-user stage needed the harness's one
   permitted retry. The first 100-user run still produced 98/100: one
   Cost-Benefit request remained a workflow proposal after retry, while one OLS
   response incorrectly claimed that its existing upload was missing. Both
   original sessions succeeded immediately with clearer single-tool prompts.
   The isolated harness prompts were clarified, and the acceptance 100- and
   200-user runs passed without retries.

These events were client/prompt diagnostics, not host saturation or lost
session evidence.

- Active session leases returned to 0.

- After evidence capture and queue verification, the Food worker received one
  maintenance restart to release retained test memory; usage returned from
  about 503 MiB to 82.75 MiB.

The 46.6 GiB value includes reclaimable filesystem cache; it is not literal
unused RAM. The host run queue briefly reached 25, but CPU did not remain
saturated and all work drained.

The ladder used one cumulative session pool: it grew from 7 pre-existing
sessions to 470/500 after the final stage. This provided only 30 sessions of
remaining LRU headroom, but did not cross the 500-session threshold. Active-run
protection and eviction behavior at or above that threshold were therefore not
exercised by this public test.

## Bottlenecks and risks

1. **Gemini TPM is the primary latency bottleneck.** The 2.7M safety budget was
   fully used and the waiting queue peaked at 185. The system preserved work,
   but p95 completion was about 5.8 minutes.
2. **Food worker memory is too close to its hard limit.** It reached 511.8 MiB
   of 512 MiB without OOM. Raise this worker to at least 768 MiB, preferably
   1 GiB, before treating the configuration as production-safe for repeated
   bursts. Do not increase its concurrency at the same time.
3. **Large uploads are not validated.** Upload code still buffers complete
   files with `await uf.read()`. Two hundred maximum guide uploads represent
   about 34.7 GB of raw data before multipart/runtime overhead.
4. **Heavy queues are not validated at 200 users.** Most InVEST queues have
   concurrency 1, so same-model bursts can serialize for much longer than this
   fast-tool pool.
5. **Root disk remains limited.** `/home` has ample space, but `/` has only
   16 GiB free. Upload/proxy/Docker temporary paths must be verified before
   large-upload testing.
